# Ticket Summary Templates

This document defines the required summary structure for each ticket type.
All `pa ticket create` calls should follow the template for the ticket's `--type`.

**Soft enforcement:** The CLI will warn and add a `needs-review` tag if the summary does not match the expected fields. The ticket is still created — warnings do not block creation.

---

## Type: `task`

Use for actionable work items with a clear scope and a single responsible team.

**Required fields:**
```
WHAT: <one-line description of what needs to be done>
WHY: <context — why this matters>
SCOPE: <key files or components affected>
```

**Example:**
```
WHAT: Add status validation to TicketStore.update() to reject unknown statuses
WHY: Currently any string is silently accepted; agents set invalid statuses that break the board
SCOPE: src/lib/tickets/store.ts, src/lib/tickets/types.ts
```

---

## Type: `review-request`

Use when asking Sinh (or another team) to review and approve a deliverable before routing it forward.

**Required fields:**
```
WHAT: <what was produced — document type + topic>
DOC: <doc_refs path to full artifact (use [type:]path format)>
REVIEW: <what to look for — approve/reject criteria>
NEXT: <what happens if approved — e.g., "route to builder for implementation">
```

**Example:**
```
WHAT: Requirements doc for kanban workflow and document management improvements
DOC: agent-teams/requirements/artifacts/2026-03-21-kanban-workflow-doc-management-improvements.md
REVIEW: Verify all 6 policy TBDs have concrete decisions, status vocabulary is agreed, summary templates cover all types
NEXT: Approve → route to builder (team: builder, status: pending-implementation); Reject → return to requirements team
```

---

## Type: `fyi`

Use for informational notifications that require no action. The reader is informed; no response expected.

**Required fields:**
```
WHAT: <what happened>
IMPACT: <who or what is affected>
ACTION: <none required | optional follow-up>
```

**Example:**
```
WHAT: Inbox migration completed — 866 files converted to 878 tickets
IMPACT: singh-inputs/inbox/ is now empty; all historical items are in the ticket system
ACTION: none required — sprint-master will triage the 287 work-report tickets in idea status
```

---

## Type: `bug`

Use for defects where behavior does not match the expected outcome.

**Required fields:**
```
WHAT: <what's broken — observed behavior>
EXPECTED: <what should happen instead>
REPRO: <steps to reproduce>
SEVERITY: <critical | major | minor>
```

**Example:**
```
WHAT: `pa ticket update PA-900 --status review-uat` fails with "ticket not found" when ID is valid
EXPECTED: Ticket status updates to review-uat successfully
REPRO: pa ticket update PA-900 --status review-uat --assignee sinh — returns error despite PA-900 existing
SEVERITY: major
```

---

## Type: `idea`

Use for raw thoughts, signals, or unscoped requests. Ideas are not commitments — sprint-master triages them.

**Required fields:**
```
WHAT: <the idea in one sentence>
WHY: <problem it solves or value it adds>
```

**Example:**
```
WHAT: Add a daily digest file generated by sprint-master from ticket comments
WHY: Current sprint-master reads inbox files which are being deprecated; digest would give Sinh a single daily read
```

---

## Type: `feature`

Use for new user-facing capabilities. More scoped than an idea but not yet fully elaborated.

**Required fields:**
```
WHAT: <feature description>
WHY: <user need or business value>
SCOPE: <estimated size — XS/S/M/L/XL>
```

**Example:**
```
WHAT: Phone UI for viewing Anytype documents and managing ticket comments
WHY: Sinh needs to review and annotate requirements docs from mobile without using the desktop app
SCOPE: L — requires new API endpoints (PA-890) and Flutter UI components
```

---

## Type: `plan-draft`

Use for daily or weekly plans emitted by the daily team. Contains a structured time budget for Sinh's review.

**Required fields:**
```
WHAT: <plan period and goals>
DOC: <doc_refs path to full plan>
BUDGET: <time budget summary>
```

**Example:**
```
WHAT: Daily plan for 2026-03-22 — focus on kanban workflow improvements and PA-877 phase 2
DOC: daily/2026/03/2026-03-22-plan.md
BUDGET: 3h deep work (PA-877), 1h review/triage, 30min admin
```

---

## Type: `work-report`

> **Note:** New standard is to add a completion comment directly on the working ticket instead of creating separate work-report tickets. This template is kept for legacy tickets and edge cases where a standalone work-report is necessary.

**Required fields:**
```
WHAT: <work done>
STATUS: <success | partial | failed>
OUTPUTS: <files, ticket IDs, artifacts produced>
```

**Example:**
```
WHAT: Executed Phase 1 of PA-877 — added status validation to TicketStore.update()
STATUS: success
OUTPUTS: src/lib/tickets/store.ts (modified), src/lib/tickets/types.ts (modified), commit abc1234 on feature/kanban-ticket-system
```

---

## Type: `question`

Use when blocked on a decision or needing clarification before proceeding. Questions are routed to the answering party.

**Required fields:**
```
WHAT: <the question>
CONTEXT: <why you're asking, what you've already tried>
BLOCKING: <ticket ID if this blocks other work, or "none">
```

**Example:**
```
WHAT: Should work-report tickets be removed from TicketType entirely or kept for legacy migration data?
CONTEXT: Requirements doc §13 leaves this open. Keeping it means soft enforcement must handle it. Removing it means 287 legacy tickets need type migration first.
BLOCKING: PA-877 (summary template enforcement implementation)
```

---

## Enforcement Notes

The `pa ticket create` command performs soft enforcement:

1. **Check:** Does the summary contain the required field labels (e.g., `WHAT:`, `WHY:`) for the specified type?
2. **If non-conforming:** Print warning to stderr: `"Summary does not match <type> template (expected fields: WHAT/WHY/...)"`
3. **Auto-tag:** Add `needs-review` to the ticket's tags
4. **No blocking:** The ticket is still created — agents are not blocked from working

Sprint-master reviews `needs-review` tagged tickets during triage and requests corrections if needed.
