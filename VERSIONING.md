# Versioning Policy — personal-assistant

personal-assistant follows [Semantic Versioning](https://semver.org/) (`MAJOR.MINOR.PATCH`).

## Version Number Rules

### PATCH — `pnpm bump:patch`

Increment the patch version for:
- Bug fixes that correct wrong behavior
- Minor tweaks to existing functionality (no new capabilities)
- Documentation and skill doc updates
- Chore commits (build fixes, dependency updates, formatting)
- Refactoring with no behavior change

**Rule of thumb:** If a user running the same commands sees the same behavior as before, it's a patch.

**Examples from PA history:**
- `fix(board): default to all projects and auto-exclude backlog/archived` → 0.3.5 → 0.3.6
- `fix(board): default excludeTags to backlog,archived on board API` → patch
- `chore: bump version to 0.3.x` commits (the bump itself is always a chore)

---

### MINOR — `pnpm bump:minor`

Increment the minor version for:
- New features or commands added to the CLI
- New agent skills or team configurations
- New API endpoints or fields
- Enhancements to existing features that add capability without breaking existing usage
- Non-breaking changes to output format or behavior

**Rule of thumb:** If users can do something new they couldn't do before, it's a minor bump.

**Examples from PA history:**
- `feat: codebase context system — R1-R4 (PA-923)` → minor (new system-level capability)
- `feat: fish completions + CLI reference for agent teams (PA-916)` → minor (new tooling)
- `feat: project-repo normalization & unified API (PA-917)` → minor (new API)
- `feat(tickets): phase 1 - add GET /api/ticket-projects endpoint` → minor (new API endpoint)
- `feat(skills): phase 4 - sprint-master triage auto-archive and suggest-backlog` → minor (new agent behavior)

---

### MAJOR — `pnpm bump:major`

Increment the major version for:
- Breaking changes to the CLI interface (removed flags, changed command names, changed output format)
- Breaking changes to the primer format or registry format that would break existing deployments
- Architectural shifts that require migration (e.g., migrating from bash scripts to TypeScript)
- Removal of previously supported workflows or file conventions

**Rule of thumb:** If an existing deployment would break or behave incorrectly after upgrading without migration, it's a major bump.

**Examples (hypothetical, PA has not yet reached v1.0.0):**
- Removing `pa deploy --background` flag → major
- Changing registry SQLite schema in a backwards-incompatible way → major
- Renaming `pa ticket` to `pa task` → major

**Note:** PA is currently pre-1.0.0 (`0.x.y`). Per semver, `0.x.y` signals unstable API. Minor bumps may include breaking changes during this phase. A `1.0.0` release would signal stable API commitment.

---

## Bump Validation

`scripts/version_bump.sh` will warn (not block) if the bump type seems mismatched:
- **Suggest `minor`** if you run `pnpm bump:patch` but `feat()` commits exist since the last tag
- **Suggest `major`** if you run `pnpm bump:minor` but `BREAKING CHANGE` commits exist since the last tag

Override with `--force` if you intentionally disagree with the suggestion.

---

## Branch Strategy

- **`develop`** — integration branch. All feature branches merge here.
- **`main`** — release-only. Only receives merges from `develop` at release time.
- **Feature branches** — named `feature/<ticket>-<topic>` (e.g., `feature/PA-899-version-strategy`), branched from `develop`.
- **Never commit directly to `main` or `develop`.**

See `.claude/branch-strategy.yaml` for the machine-readable config.

---

## Release Process

```
feature/PA-NNN-topic  →  develop  →  main  (tagged vX.Y.Z)
```

1. Merge feature branch into `develop`
2. When ready to release, merge `develop` into `main`
3. Run `pnpm bump:patch|minor|major` on `main`
   - This generates a changelog draft, builds, commits, tags, and pushes
4. Rebuild NixOS: `nixos-rebuild switch --flake .#hostname`

## Changelog

CHANGELOG.md is auto-generated by [git-cliff](https://git-cliff.org/) using the config in `cliff.toml`.

**To generate a changelog draft for the current unreleased changes:**
```bash
git cliff --unreleased
```

**To regenerate the full changelog:**
```bash
git cliff --output CHANGELOG.md
```

The changelog follows [Keep a Changelog](https://keepachangelog.com/) format, grouping commits by type:
- **Added** — `feat` commits
- **Fixed** — `fix` commits
- **Changed** — `refactor` commits
- **Documentation** — `docs` commits
- **Dependencies** — `chore(deps)` commits
- **Reverted** — `revert` commits
