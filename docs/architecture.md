# Architecture

## Overview

`pa` is a TypeScript CLI that orchestrates AI agent teams. It generates structured markdown "primers" from YAML team configs and skill documents, then feeds them to `claude` CLI for execution.

```
User runs:  pa deploy <team>
                │
                ▼
        ┌──────────────┐
        │  Parse YAML   │  teams/<team>.yaml
        │  team config   │
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │  Read skills  │  skills/<agent-skill>.md + skills/global/*.md
        │  (markdown)   │
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │  Generate     │  primers/<team>-<deploy-id>-primer.md
        │  primer doc   │
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │  Spawn claude │  claude --dangerously-skip-permissions --print <prompt>
        │  (background) │  → logs/<team>-<deploy-id>.log
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │  Registry     │  ~/Documents/ai-usage/deployments/registry.db
        │  (SQLite)     │  Events: started → pid → completed/crashed
        └──────────────┘
```

## Key Concepts

### Primer

A primer is a self-contained markdown document that tells `claude` everything it needs to know for a deployment. It contains:

1. **Deployment context** — deploy ID, team name, timestamp, registry paths
2. **Team description** — from the YAML config
3. **Agent sections** — each agent's role + full skill document inlined
4. **Global skills** — applied to all agents (standards, conventions)
5. **Objective** — what the team should accomplish
6. **Deployment instructions** — standard steps to follow

Generated by `src/lib/primer.ts`.

### Registry

A SQLite database at `~/Documents/ai-usage/deployments/registry.db`. The schema has two tables:

- **`registry_events`** — all deployment lifecycle events (started, pid, completed, crashed)
- **`registry_fts`** — FTS5 full-text search index over event summaries and metadata

Example events:
```sql
-- Events are rows in registry_events, not JSONL lines
SELECT deployment_id, team, event, status, summary FROM registry_events
WHERE deployment_id = 'd-7ae0a9' ORDER BY timestamp;
```

The `pa status` command reads the SQLite registry and checks PID liveness to compute deployment status. WAL mode enables concurrent reads without blocking.

> **Legacy:** A JSONL file at `registry.jsonl` is maintained via dual-write (`PA_REGISTRY_DUAL_WRITE=1`) for backwards compatibility. It is deprecated and will be removed in a future release. Use `pa registry migrate` for one-time migration from JSONL → SQLite.

### Path Layering

PA uses a layered path system for teams and skills:

1. **PA_CONFIG** (user overrides) — checked first, shadows PA_HOME
2. **PA_HOME** (read-only install) — Nix-installed teams/skills

This allows users to customize teams without modifying the Nix store.

## Deployment Modes

| Mode | Flag | Behavior |
|---|---|---|
| Background | *(default)* | `nohup` + detached process, logs to file, PID tracked |
| Foreground | `--foreground` | Runs `claude` with `--dangerously-skip-permissions`, inherits stdio |
| Interactive | `--interactive` | Runs `claude` normally (user approves each tool call) |
| Dry run | `--dry-run` | Generates primer, prints it, exits |

## Daily Lifecycle

The `pa daily` command wraps `pa deploy` with mode-specific objectives:

- **plan** (05:00) — Read yesterday's summary, check avo tasks, write draft plan
- **progress** (14:00) — Compare plan vs actual, generate progress report
- **end** (21:00) — Full day summary, set tomorrow's priorities

Each mode creates a temp YAML file with the objective injected, then calls `deployCommand()` internally.

## Systemd Integration

`pa schedule` creates two systemd user units per timer:

- `pa-<name>.service` — `Type=oneshot`, runs the `pa` command
- `pa-<name>.timer` — `OnCalendar=` schedule, `Persistent=true`

Timer management: `pa timers` (list), `pa remove-timer` (stop + disable + delete).

## Source Layout

```
src/
├── cli.ts              # Commander.js program definition
├── commands/           # Each command is a standalone function
│   └── *.ts            # Exported as: fooCommand(args)
├── lib/                # Shared libraries
│   ├── types.ts        # All interfaces (TeamConfig, RegistryEvent, DeploymentStatus, PAConfig)
│   ├── config.ts       # loadConfig() — merges env vars + config file
│   ├── paths.ts        # Path getters (getHomeDir, getDataDir, getRegistryPath, etc.)
│   ├── registry.ts     # appendRegistryEvent() + readRegistry() (SQLite-backed)
│   ├── registry-db.ts  # SQLite schema, FTS5 search, analytics views
│   ├── yaml-parser.ts  # parseTeamYaml() — validates team YAML structure
│   └── primer.ts       # generatePrimer() — assembles the primer document
└── utils/
    └── process.ts      # spawnDetached() — nohup-style background process
```
